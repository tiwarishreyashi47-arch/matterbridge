## v1 Technical Baseline (reference for Phase 2)

v1 = current codebase, built on synthetic data. Phase 2 builds on top of it.

- Framework: Next.js App Router, TypeScript, Tailwind CSS, ESLint. No `/src` directory; default `@/*` alias; no React Compiler.
- Data source: `MatterBridge_Database_Completed.xlsx` -> `scripts/convert_excel_to_json.py` -> `data/raw/*.json`, `data/matters/MAT-001.json`, `data/matters/MAT-002.json`, `data/knowledge_chunks.json`, `data/matter_index.json`, `data/validation_report.json`.
- Storage: file-backed JSON only. No database, vector store, auth, or RBAC.
- Types: `lib/types/matter.ts` (`MatterBundle`, `Workstream`, `Document`, `DocumentSection`, `LegalIssue`, `AIFinding`, `FindingCitation`, `CounselEngagement`, `CounselOutput`, `Decision`, `InstitutionalMemory`, `KnowledgeChunk`, `EvidencePacket`).
- Data access: `lib/data/matter-service.ts`, `issue-mapping.ts`, `evidence-service.ts`, `counsel-service.ts`, `access-service.ts`.
- Retrieval: deterministic matter/workstream filtering, lexical ranking, bounded evidence packets over `knowledge_chunks.json`; source/chunk IDs preserved.
- LLM: `app/api/opinion-review/route.ts` calls Gemini `generateContent` server-side (`GEMINI_API_KEY`, `GEMINI_MODEL`); structured JSON output; returned source IDs validated against retrieved scope; stored review used as fallback.
- Routes: `/`, `/evidence`, `/counsel-review`, `/settings`, `/matters/[matterId]`, `/matters/[matterId]/workstreams/[workstreamId]`, `/matters/[matterId]/counsel-brief`, `/matters/[matterId]/opinion-review`, `/matters/[matterId]/legal-decision`, `/matters/[matterId]/institutional-memory`, `/counsel-workspace/[matterId]`.
- Trust states: SUPPORTED, INFERRED, INFORMATION_MISSING, REQUIRES_LEGAL_JUDGMENT.
- Not persisted in v1: uploads, comments, live review results, decision edits.

v1 -> Phase 2 changes:

| Area | v1 | Phase 2 |
|---|---|---|
| Data source | Excel -> JSON | Uploaded documents -> extraction -> lawyer review |
| Storage | File-backed JSON | Postgres (Supabase) + object storage + pgvector |
| Facts | Fixed fields on records | Assertions with citations, trust state, review status |
| Citations | Authored source/chunk IDs | Model-returned quotes verified against page text |
| Issues | Authored in data | Generated by versioned rules, contradiction and gap detection |
| Matter types | MAT-001, MAT-002 shapes | Versioned templates (Recovery, Employment, Financing, Generic) |
| Home | Matter dashboard | Org context graph + filterable matter list |
| Lawyer input | Local, non-persistent | Persistent accept / edit / reject with audit trail |

# Phase 2 - v2: Document-Driven Legal Company Brain (Active)

## Goal

Replace the Excel -> JSON data pipeline with a document-driven pipeline. Lawyers create a matter from a matter-type template, upload documents, and MatterBridge extracts, cites, and populates the matter by default. Everything extracted is visible immediately, marked **Unreviewed**, and is confirmed or corrected by a lawyer through a review queue.

The same pipeline must serve a complex matter (MAT-001 Recovery) and a simple one (MAT-002 Employment/HR). Complexity lives in template configuration and data volume, never in separate code paths or schemas.

## Product decisions (do not change without updating this plan)

- **Users:** a 10–15 person in-house legal team. **No permissions in Phase 2** — every user can see every matter.
- **Home screen:** an organisational context graph of matters grouped by practice area, plus a filterable matter list ("My matters", practice area, stage, risk, deadline, counterparty, firm). Graph and list share the same filter state.
- **Default population:** extracted facts appear in matter screens immediately with an Unreviewed badge. Review is a queue, not a gate.
- **Lawyer wins:** a lawyer correction is a new assertion that supersedes extraction. Re-extraction never overwrites accepted or user-entered assertions.
- **Matter types are data, not code:** templates are stored in the database, validated by a schema, and versioned, so a Head of Legal configuration UI can be added later without refactoring.
- **Trust states:** SUPPORTED, INFERRED, INFORMATION_MISSING, REQUIRES_LEGAL_JUDGMENT. No fake confidence percentages. No final legal opinions.

## Engineering guardrails

Permission seams — build these now so access control can be added later without a rewrite:
- All reads go through `lib/data/*` services. No component, page, or API route queries tables directly.
- Services take a list of matter IDs. For now, call `allMatterIds()`; later this becomes `visibleMatterIds(user)`.
- The graph is derived from a matter set: fetch matters first, then compute entities, links, and bridge counts from that set only. Never cache a global graph.
- Every matter-scoped row stores `matter_id` directly (documents, spans, assertions, issues, engagements, questions, decisions).
- AI retrieval and prompt assembly always receive an explicit matter-ID list.
- Knowledge items reference matters and assertions by ID; they do not copy matter facts into free text.

Other guardrails:
- Keep the model provider behind an interface (`lib/ai/provider.ts`); no direct SDK calls from features.
- Every extraction run records model, prompt version, template version, and input document IDs.
- Do not add LangChain, LlamaIndex, or a graph database. Postgres + JSONB + pgvector is sufficient.

## Target data model (summary)

Evidence: `document` (matter_id, doc_type, file_path, file_hash, status, zone), `page`, `span` (page, char range, bbox, text).
Entities: `entity` (kind, display_name), `matter_entity` (matter_id, entity_id, role), `relation` (from_entity, to_entity, relation_type, assertion_id).
Assertions: `assertion` (matter_id, entity_id, attribute, value JSONB, trust_state, status: proposed/accepted/rejected/superseded, source: extraction/user/seed/rule, run_id), `assertion_evidence` (assertion_id, span_id, stance: supports/contradicts).
Analysis: `issue` (matter_id, workstream_id, rule_code, rule_version, status, severity, requires_legal_judgment), `issue_basis` (issue_id, assertion_id or missing_item_key, basis_type).
Collaboration: `engagement`, `brief`, `question` (issue_id), `opinion_point` (assertion/evidence refs), `decision` (issue refs, rationale, decided_by).
Organisation: `practice_area`, `matter_type_template` (versioned config), `matter` (practice_area, template_id, template_version, owner_id, stage, risk, next_deadline), `matter_member` (user_id, role: lead/member/reviewer — workflow only), `matter_link` (from_matter, to_matter, link_type: lifecycle_successor/related/precedent), `user` (name, team_role).
Operations: `extraction_run`, `job`, `audit_event` (append-only), `knowledge_item`.
Derived: `current_fact` view = latest accepted-or-proposed assertion per (entity, attribute), with user > accepted > proposed precedence.

## Matter-type template contract

Templates are JSON validated by `TemplateSchema` (Zod) in `lib/templates/schema.ts`. A template defines:
- `practice_area`, `name`, `version`, `status` (draft/published)
- `stages` (ordered lifecycle stages)
- `workstreams` (skeleton, nesting allowed)
- `entity_roles` (e.g. borrower, guarantor, prior_mortgagee; employee, manager)
- `document_types`, each with `fields` (key, label, type, description, required, entity_role, cardinality)
- `expected_documents` (checklist keys; missing items become INFORMATION_MISSING issues)
- `rules` (rule_code + parameters only — e.g. `{ "rule": "valuation_stale", "params": { "max_age_months": 12 } }`)

Rule logic lives in code (`lib/rules/*`, each rule has a code and version). Templates select rules and set parameters; they never contain executable logic. This is the boundary that keeps a future no-code configuration UI safe.

Matters pin a template version. Publishing a new version affects new matters only; existing matters migrate by explicit action.

Seed templates: `recovery.v1`, `employment.v1`, `financing.v1` (light, for the lifecycle demo), and `generic.v1` (fallback: parties, dates, amounts, obligations, key events).
